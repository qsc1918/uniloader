## 2. ★ 为什么 26.3 没有 intermediary 是**正常的**（不是阻塞项）

> 结论修正（2026-10-07，用户指出 + 三处实测证实）：**MC 26.1 起 Mojang 不再混淆**，
> 因此既不需要映射，也不会发布映射。最初把它写成「阻塞项」是判断错误，此处改正。

### 证据一：官方版本元数据里已经没有映射了

```bash
# 26.3 的 downloads 只有 client / server
$ curl -sS <26.3 的 version json> | python -c "import json,sys;print(sorted(json.load(sys.stdin)['downloads']))"
['client', 'server']

# 1.21.11（最后一个混淆版）则带 mappings
['client', 'client_mappings', 'server', 'server_mappings']
```

实测三个版本：`1.21.11` → 有 `client_mappings`/`server_mappings`；`26.3` 与 `26.4-snapshot-3` → **都没有**。
`maven.fabricmc.net` 上的 intermediary 停在 1.21.11，正是这个原因：**没有混淆就不需要 intermediary**。

### 证据二：loom 自己就是这么判的（`fabric-loom` 工作区源码）

```java
// MinecraftMetadataProvider.java:95
public boolean isUnobfuscated() {
    return getVersionMeta().isVersionOrNewer(Constants.RELEASE_TIME_1_21_11_UNOBFUSCATED_SNAPSHOTS)
            && !getVersionMeta().downloads().containsKey("client_mappings");
}

// LoomGradleExtensionApiImpl.java:155-161
productionNamespace.convention(isUnobfuscated() ? MappingsNamespace.OFFICIAL : MappingsNamespace.INTERMEDIARY);
useIntermediateMappings.convention(() -> !isUnobfuscated());
defaultMixinRemapType.convention(isUnobfuscated() ? STATIC : MIXIN);
```

另外 `UnobfuscatedMappingNsCompleter` 会把 official 名**复制进** intermediary 命名空间，
即未混淆版本下 **official == intermediary == named，三者同名**。

### 证据三：内核侧的默认值本来就是 official

- `SystemProperties.RUNTIME_MAPPING_NAMESPACE` 的注释：*"default: **official for unobfuscated games**,
  named for obfuscated games while DEVELOPMENT is set or intermediary otherwise"*；
- `MappingConfiguration.computeRuntimeNamespace()`：**没有 mappings 文件时返回 `official`**；
- `MappingConfiguration.getDefaultModDistributionNamespace()`：`runtime != official` 才退回 intermediary，
  否则保持 `official`；
- `MinecraftGameProvider.initialize()`：`gameNs` 与 `runtimeNs` 都是 official →
  `!gameNs.equals(runtimeNs)` 不成立 → **完全不做反混淆**；
- `FabricLoaderImpl.setup()`：`remapRegularMods = isDevelopmentEnvironment()` 为 false；
  即便为 true，`RuntimeModRemapper.remap()` 也会因为 `modNs.equals(runtimeNs)`（都是 official）直接返回。

### 这意味着什么（对 UL 是好消息）

| | 26.3（未混淆） | <= 1.21.11（混淆） |
|---|---|---|
| 运行时命名空间 | `official`（== Mojang 真实名） | 默认 `intermediary`（dev 为 `named`） |
| mod 分发命名空间 | `official` | `intermediary` |
| 需不需要重映射 | **完全不需要** | 需要（Fabric → named） |
| D1 的目标（统一到 mojmap） | **免费得到** | 需要用 D1 的机制去挣 |

也就是说：**在 26.3 上，内核与四家 mod 天然处于同一命名空间**，
D1 讨论的「统一命名空间」这件事在这个版本上自动成立。
`docs/stage0/T0.3-D1-namespace-experiment.md` 里那四处门闸（G1–G4）**只在支持 <= 1.21.11 时才适用**。

### 因此版本矩阵的决策不变，但理由更清楚了

- 首个目标版本仍取 **26.3**（与 NeoForge / Forge / fabric-api 一致）；
- 不需要为 26.3 找 intermediary，也不需要自维护映射；
- 如果将来要向下支持 1.21.11（那里有完整的中介映射与庞大的存量 mod），
  D1 的机制与四处门闸就是那时的施工图。

## 3. 构建侧的两处实测结论（已修复在 fork 里）

| 现象 | 根因 | 处理 |
|---|---|---|
| `./gradlew build` 在 `:proguardJar` 失败：`can't find superclass or interface java.lang.Object` | 上游把 Java 8 工具链的 rt.jar 硬编码为 `jre/lib/rt.jar`；当解析到的是 **JRE**（而非 JDK）时，路径是 `lib/rt.jar`，ProGuard 于是拿到一个不存在的 libraryjar | fork 内改为两种布局都探测（`loader/build.gradle`，注释标注为 `UniLoader fork patch (T0.1)`） |
| 用 Gradle 9.7.1 构建时 `:minecraft` 报 `Could not get unknown property 'sourceSets' for project ':' of type DefaultProjectDependency` | `minecraft/build.gradle` 里 `implementation project(":").sourceSets.main.output` 在 9.7 上 `project(":")` 返回 ProjectDependency | **不改上游代码**：按上游指定的 9.1.0 构建（wrapper 已锁定），并在本文档记录，避免后人误升 Gradle |

## 4. 网络与代理（本机环境相关，不进代码）

本机在受限网络下，构建与实验的下载需要代理。用环境变量传入即可，**不要写进仓库文件**：

```bash
export https_proxy=http://127.0.0.1:7897
export http_proxy=http://127.0.0.1:7897
export GRADLE_OPTS="-Dhttps.proxyHost=127.0.0.1 -Dhttps.proxyPort=7897 -Dhttp.proxyHost=127.0.0.1 -Dhttp.proxyPort=7897"
```

Gradle 分发包（9.1.0）在国内镜像上可用：`https://mirrors.cloud.tencent.com/gradle/gradle-9.1.0-bin.zip`
（`services.gradle.org` 会 307 跳到 GitHub Release，在受限网络下不稳定）。
