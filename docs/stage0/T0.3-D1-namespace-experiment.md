## 5. mixin 注解字符串与 refmap 的实际行为（生产环境与开发环境的关键差异）

### 5.0 观察（不是断言，是 tiny-remapper 的实际行为）

- mixin（内核默认路径）：@Inject(method=...) 字符串 保持 intermediary（方法样本 2 个，MixinExtension=未启用）
- static（显式启用 MixinExtension）：@Inject(method=...) 字符串 保持 intermediary（方法样本 2 个，MixinExtension=启用）

| remap 类型 | MixinExtension | `@Inject(method=...)` 字符串 | refmap.json |
|---|---|---|---|
| `mixin`（loom 默认，内核默认路径） | 不启用 | [method_34997, method_33914] | 原样保留 |
| `static`（manifest 显式声明） | 启用 | [method_34997, method_33914] | 原样保留 |

关键事实：mixin 注解里的目标名是**字符串常量**，字节码重映射不会碰它。
loom 用 refmap.json 的 `named:intermediary` 键在运行时把它翻译过去（编译用 named、发布打成 intermediary）。
运行时命名空间一旦变成 named，这把钥匙就对不上锁了——这是 D1 在生产环境最容易踩空的一处，
必须在阶段 1 显式处理（见第 7 节 G3）。

## 7. 内核必须改动清单（本实验查证的四处门闸）

| 编号 | 位置 | 现状 | 必须做什么 |
|---|---|---|---|
| G1 | `FabricLoaderImpl.setup()`（`remapRegularMods = isDevelopmentEnvironment()`） | 生产环境恒为 false | 改为生产也 remap（用 `ul.remapFabricMods` 开关控制） |
| G2 | `RuntimeModRemapper.getRemapClasspath()` | 缺 `fabric.remapClasspathFile` 就抛异常；**且实测该 classpath 必须是「源命名空间」的 MC+库** | 生产环境必须提供该文件，内容为 **intermediary 名**的 MC 与库（本实验用对照桩 jar 实测：只给 named 名时，成员名重映射会静默不生效） |
| G3 | mod jar 内的 `refmap.json` 与 mixin 注解字符串（键 `named:intermediary`） | 运行时变 named 后对不上；**实测 MixinExtension（static 模式）也不会改写 `@Inject(method=...)` 字符串** | 内核自己解决：把 `FabricMixinBootstrap` 里 dev-only 的 `MixinIntermediaryDevRemapper` + `mixin.env.remapRefMap=true` 放开到生产（Fabric 官方机制，只是被 `isDevelopment()` 挡住了） |
| G4 | `MinecraftGameProvider.initialize()` 的 `!gameNs.equals(runtimeNs)` | 两者都设成 named 会跳过反混淆 | 必须保证 MC 本体已经是 mojmap（由安装器预先 remap），否则类名全错 |

G4 尤其容易踩：把 `fabric.gameMappingNamespace` 与 `fabric.runtimeMappingNamespace` 都设成 named
确实能「跳过 deobfuscate」，但**只有在 MC 本体已经是 mojmap 名字时才是对的**；
若喂进去的是官方混淆 jar，跳过反混淆的结果是全线对不上名。
